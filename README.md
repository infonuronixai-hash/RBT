# Robotic Arm Studio

Desktop application to drive a 6-axis hobby-servo robotic arm through an **Arduino Uno**
over USB, with **record and playback** of motion.

```
d:\RG
├── run.bat                     double-click to launch (installs pyserial if needed)
├── build.bat                   package a standalone exe + Windows installer
├── app\                        Python desktop application
│   ├── main.py                 entry point / CLI
│   ├── ui.py                   HUD interface and kinematic view
│   ├── widgets.py              canvas-drawn controls (sliders, buttons, switches)
│   ├── theme.py                palette, fonts, colour blending for the glow effects
│   ├── robot3d.py              kinematic chain + shaded polygon renderer for the 3D view
│   ├── mesh.py                 STL loader: segments the scan and rigs it to the joints

│   ├── vision.py               board vision: warp, occupancy, turn detection
```

## Installation

### What you need

| | |
|---|---|
| **Windows 10/11** | the packaged build and `run.bat` are Windows; from source it also runs on Linux/macOS with `python3-tk` installed |
| **Python 3.10+** | from [python.org](https://www.python.org/downloads/) — tick *Add python.exe to PATH*. Tkinter ships with it. |
| **Arduino IDE** | to flash the Uno once — [arduino.cc/en/software](https://www.arduino.cc/en/software) |
| **Git** | only to clone; a ZIP download works too |

### Option A — run from source (recommended while developing)

```bat
git clone https://github.com/infonuronixai-hash/RBT.git
cd RBT
python -m pip install -r app\requirements.txt
python app\main.py --sim
```

`--sim` starts the built-in simulator so you can explore the app before any hardware is
connected. Once the Uno is flashed and plugged in, start without `--sim`, press **SCAN**,
pick the port and **CONNECT**. `run.bat` does the same thing with a double-click and
installs `pyserial` if it is missing.

The core app needs only `pyserial`. The other lines in `requirements.txt` are optional
and load lazily when their mode is switched on:

| Feature | Package |
|---|---|
| Chess mode (`CHESS` toggle) | `chess` |
| Board camera inside chess mode, and `vision_tool.py` | `opencv-python`, `numpy` |

If a package is missing the toggle refuses politely and the log tells you the exact
`pip install` line.

### Option B — installer, no Python needed

Build it once on a machine that has Python, then hand out one file:

```bat
build.bat
```

That produces `dist\RoboticArmStudio-1.0.0-Setup.exe`. It installs per-user with no
administrator password, adds Start-menu entries, and keeps its own config in
`%LOCALAPPDATA%\RoboticArmStudio\`. See *Handing it to someone else* below for the
portable single-file variant and the antivirus caveat.

### Check it works

```bat
python tests_core.py       engine, sequences, serial layer   (no hardware)
python tests_ui.py         opens the real window, runs a record/play cycle
python tests_chess.py      rules, built-in engine, move planning
```

All suites run against the simulator; none need an Arduino or a camera.

## 1. Flash the Arduino

1. Open `firmware\robotic_arm\robotic_arm.ino` in the Arduino IDE.
2. Board: **Arduino Uno**, pick the right COM port.
3. Upload. The board prints `RDY RoboArm 1.0` at **115200 baud**.

Default servo pins:

| # | Joint       | Pin |
|---|-------------|-----|
| 0 | Base rotate | D3  |
| 1 | Shoulder    | D5  |
| 2 | Elbow       | D6  |
| 3 | Wrist pitch | D9  |
| 4 | Wrist roll  | D10 |
| 5 | Gripper     | D11 |

**Power the servos from a separate 5–6 V supply rated 2 A or more, and tie its ground to
the Arduino's ground.** Six servos will brown out the Uno's regulator and reset the board
if you run them off the USB 5 V pin. See [docs/WIRING.md](docs/WIRING.md).

## 2. Run the application

Double-click **`run.bat`**, or from a terminal:

```bat
python -m pip install pyserial
python app\main.py
```

Other ways to start:

```bat
python app\main.py --list          list serial ports and exit
python app\main.py --port COM5     connect on startup
python app\main.py --sim           run the UI with no hardware attached
python app\main.py --open FILE     load a sequence on startup
```

Pick the Arduino's port in the top bar and press **Connect**. The status dot turns green
and the firmware banner appears in the log.

## Interface

A three-column HUD console: manual control on the left, the 3D kinetic view in the middle,
telemetry and the motion sequence on the right, with a metrics strip along the bottom.

**Kinetic view.** The arm shown is the real STL model in
`app/assets/robotic_arm_6axis.stl`. An STL is loose triangles with no hierarchy, so
[mesh.py](app/mesh.py) recovers the rig geometrically: weld vertices, flood-fill into
separate solids, order those along the arm, cut them into six joint groups, and take each
group's root as its pivot. Coplanar triangle pairs are merged into quads, halving the
polygon count that the renderer has to push. **The pose the model was exported in is the
home pose** - every joint reading 90 deg shows the CAD pose, and the sliders articulate
from there. Swap in a different STL and the group cuts in `mesh.py` need retuning; if the
file is missing the app falls back to a procedural arm and still runs.

[robot3d.py](app/robot3d.py) drives that chain from the live joint angles, then projects,
back-face culls, depth sorts and flat-shades it onto a Tk canvas — no OpenGL and no numpy, so the app still
installs with nothing but pyserial. Drag to orbit, wheel to zoom, or use the FRONT / SIDE
/ TOP / ISO presets, and switch between REALTIME, WIREFRAME, TRANSPARENT and ISOLATE.
A static scene is not redrawn at all (the view reports IDLE), and the pedestal and floor
sit on a cached layer that is only repainted when the camera moves, so a moving frame
repaints roughly half the model.

**Telemetry is real or blank.** Angle and speed are measured — speed from how fast the
commanded pose is actually changing. Load, temperature, voltage and current show `--`,
because hobby servos have no feedback wire and the board has no power sensing. Fit an
INA219 and a thermistor and those tiles have something to show; until then they are not
filled with invented numbers.

The rest of the styling:  Stock ttk widgets cannot draw glows or capsule tracks, so the joint
sliders, buttons and switches in [app/widgets.py](app/widgets.py) are painted by hand on
canvases — each joint gets its own accent colour, a glowing fill and a live degree readout.
The kinematic view renders a side elevation of the arm over a perspective floor, with
base-rotation and wrist-roll dials and an end-effector crosshair.

Everything is measured in display-scaled pixels, so it renders correctly on a 100% or a
200% display. Font sizes stay in points — Tk's own DPI scaling converts those.

## Two independent modes

The app starts as a **plain manual controller**: sliders and jog buttons drive the arm and
nothing else is on screen. Recording and playback are a separate workbench you switch on
with the **Record & Play** checkbox in the toolbar, and switch off again when you just want
to drive the arm by hand.

Manual control never stops working. It stays live while the record/play panel is open,
while a recording is running, and even during playback — touching a slider or a jog button
takes over immediately and stops the running sequence (the log says so). The arm answers
the controls at all times.

## Controlling the arm

- **Sliders** drive each joint live; moves are streamed to the board at 25 Hz.
- **-/+** jog by the step size in the Jog step box.
- **Speed** sets the firmware slew rate in degrees/second, so the arm eases into position
  instead of snapping (which is what strips gears and browns out supplies).
- **Home / Hold / Relax** — go to the home pose, energise the servos, or detach them.
  *Relax lets the arm fall under its own weight; support it first.*
- **Arm → Joint setup** sets per-joint min/max travel, home angle, mechanical trim and
  direction invert. Limits are enforced in the app *and* pushed to the firmware, so a bad
  sequence can't drive a joint into its end stop. **Arm → Store settings in EEPROM** makes
  the limits survive a power cycle.

## Recording and playing back

Tick **Record & Play** in the toolbar to reveal this panel. Two recording modes, switched
with the radio buttons:

**Continuous** — press **● Record** and move the arm. Poses are sampled at 20 Hz and
redundant frames are trimmed automatically on stop, so a static pause becomes a single
held frame instead of hundreds of duplicates. This captures the *feel* of a hand-driven
move.

**Keyframe** — drive the arm to a pose and press **Add pose**. Each frame gets a 1 s
travel time and a 0.3 s dwell; both are editable with **Edit timing**. This is the
repeatable, pose-to-pose way to program a pick-and-place cycle.

Playback interpolates linearly between frames at 25 Hz and streams the result to the board:

- **▶ Play** — from the start, or from the selected frame if one is highlighted.
- The Play button becomes **Pause**, then **Resume**, while a sequence runs; **■ Stop**
  ends it. **Loop** repeats, and playback speed runs from 0.25× to 3×.
- **Go to** jumps the arm to the selected frame; **Update** overwrites it with the current
  pose; **Up/Down** reorder; **Rescale time** stretches or compresses the whole move;
  **Simplify** thins out a dense recording within a degree tolerance you choose.

Sequences save as readable JSON in `sequences\`:

```json
{ "version": 1, "name": "demo_wave_hello", "joints": ["base", "shoulder", ...],
  "frames": [ { "t": 0.0, "angles": [90,90,90,90,90,20], "hold": 0.3, "label": "home" } ] }
```

Two demos ship in `sequences\`: `demo_wave_hello.json` (gentle, good for a first hardware
test) and `demo_pick_and_place.json`.

## Teach mode (hand-guided recording)

Hobby servos can't report where they've been pushed, so teaching by physically moving the
arm needs position feedback. Wire six potentiometers to **A0–A5** — either a knob-per-joint
teach pendant, or pots geared to the joints themselves — and tick **Teach mode**:

1. The firmware detaches the servos so nothing fights you.
2. Pot positions stream back as the live pose at ~16 Hz.
3. Press **● Record** and pose the arm by hand.
4. Untick Teach mode; the servos re-engage holding the last pose.

Without pots the checkbox still works but the readings are meaningless — use slider
recording instead.

## Chess mode

Switch on **CHESS** in the toolbar and the lower centre panel becomes a game: click a
piece, click its destination, and the arm plays the reply. Manual control stays live
throughout, exactly as in the other modes.

```bat
python -m pip install chess
```

**Opponent.** A built-in alpha-beta search (levels 1-3, depth 1-3) that needs no
external program; level 3 answers in a second or two. If you have a Stockfish
executable, `chess_game.make_engine` will use it when given the path - a very large
strength jump.

**Teaching the board to the arm.** Hobby servos have poor absolute accuracy but good
repeatability, so squares are *taught*, not computed. Park the gripper on **a1** with the
jaws around a piece and press `a1`; repeat for `h1`, `a8`, `h8`. Then raise the arm from a1
to a safe travel height and press `HOVER`. Finally park it over a bin for captured pieces
and press `BIN`. Every other square is interpolated between the four corners in joint
space; the map is saved and reloaded automatically. Until it is taught, moves show on the
board only and the log says so.

**How a move is played.** [chess_arm.py](app/chess_arm.py) turns a move into an ordinary
keyframe sequence - hover, descend, grip, lift, travel, descend, release, home - so the
existing player, its interpolation and the manual-override safety all apply. A capture
first carries the taken piece to the bin; castling moves the rook too; en passant removes
the pawn from the square it actually stands on. The sequence shows in MOTION SEQUENCE
while it runs. Touching a slider mid-move stops the arm; the game continues and the log
asks you to finish the move by hand.

**Camera.** Switch on CAMERA in the chess panel (or pick CAM in the Kinetic View) and the
feed appears in the Kinetic View. The first time, it asks you to **click the four board
corners** on the feed, clockwise from top-left — that is the whole calibration, saved
automatically and reused next time. Press `EMPTY` once with the board cleared for the
most reliable detection, `CALIBRATE` to redo the corners after the camera has been moved,
and `NEXT CAM` to cycle cameras (laptops list the lid webcam first). Nothing has to be run
outside the app; `vision_tool.py` remains as a standalone tuning tool. Once calibrated the
Kinetic View shows the feed and, alongside it, the detection: the raw feed with the calibrated quad on the
left, the rectified board with occupancy rings and the detector state (WATCHING /
IN_MOTION / SETTLING) on the right — the same view as the vision tool, in-app. Switch
back to 3D any time to watch the arm instead. Detection works the same way either way: it does not recognise pieces, it plays every
legal move on a scratch board and picks the one whose resulting occupancy matches what
the camera saw. Captures, castling and en passant fall out of that without special
cases. If more than one legal move matches, it highlights the squares and asks you to
click instead - it never guesses.

## Board vision (prototype)

Groundwork for having the arm play chess: a fixed camera watches the board, works out
on its own when you have finished a move, and reports it. Entirely separate from the arm
app — nothing in `main.py` imports it, so the packaged build stays free of OpenCV.

```bat
python -m pip install opencv-python
python app\vision_tool.py --demo        synthetic board, no camera needed
python app\vision_tool.py --list        list cameras that actually open
python app\vision_tool.py --camera 1    use a specific camera
python app\vision_tool.py --image b.png run against a still photo
```

**It does not recognise pieces.** Telling a knight from a bishop from above is hard and
fails often; deciding whether a square is *occupied* is easy. Since the game state is
known, "e2 emptied and e4 filled" identifies the move on its own. Anything more complex —
a capture (one square changes), castling (four) — is reported for the game logic to
resolve against the legal move list, never guessed.

**Turn detection needs no button.** Frame-to-frame difference over the board says when a
hand is in shot. Nothing is analysed during movement; only once the scene has been still
for a moment (`SETTLE`) is the board compared. Hovering, or picking a piece up and putting
it back, produces no move.

To use it: press START, then SET CORNERS and click the four board corners, then EMPTY
BOARD to capture a reference of the bare board, then WATCH.

Two things matter more than anything else in the code:

- **Lock exposure and focus** (there is a button). A webcam's auto-exposure re-meters when
  a hand enters the frame, changing the brightness of *every* square at once — the most
  common cause of phantom detections.
- **Mount the camera rigidly**, looking straight down. Overhead matters because tall
  pieces hide the squares behind them at shallow angles. Bump the camera and the
  calibration is void.

Occupancy is compared in colour, not greyscale, because a piece whose brightness happens
to match the square beneath it vanishes in greyscale — a real case, not a hypothetical.

## Serial protocol

115200 baud, one ASCII command per line. Usable from any terminal, not just this app.

| Command | Effect |
|---|---|
| `PING` | handshake → `OK PONG RoboArm 1.0 6` |
| `G` | read position → `POS 90 90 90 90 90 20` |
| `M a0 a1 a2 a3 a4 a5` | move all joints (`-` keeps a joint where it is) |
| `S <i> <angle>` | move one joint |
| `J <i> <delta>` | jog one joint |
| `SPD <deg/s>` | slew rate, 0–600 (0 = instant) |
| `HOME` | go to the home pose |
| `ATT` / `DET` | attach / relax servos |
| `LIM <i> <lo> <hi>` / `LIMS` | set / list travel limits |
| `SAVE` / `LOAD` | limits + speed to/from EEPROM |
| `TEACH 0\|1` | relax and read pots on A0–A5 |
| `STREAM <ms>` | push `POS` lines every *ms* (0 = off) |

Replies are prefixed `OK`, `ERR`, `POS`, `LIM` or `RDY`.

## Handing it to someone else

`build.bat` packages the app so it runs on a Windows machine with **no Python
installed**, and wraps it in an installer:

```bat
build.bat
```

You hand out one file, `dist\RoboticArmStudio-1.0.0-Setup.exe` (12 MB). It installs
per-user by default so it needs no administrator password, offering the all-users
choice on its first page, and it lays down the app, an uninstaller, Start menu
entries, `WIRING.md` and the Arduino sketch.

`build.bat portable` additionally produces `dist\portable\RoboticArmStudio.exe`, a
single file that runs from a USB stick with nothing installed - but read the antivirus
note below before choosing it.

### Where an installed build keeps its files

It cannot write next to its own exe: Program Files is read-only for a standard account.
So the packaged app keeps its config and sequences in
`%LOCALAPPDATA%\RoboticArmStudio\` and copies the demo sequences there on first run.
Uninstalling leaves that folder alone, so recorded motions and joint calibration
outlive the program. Running from source is unchanged - `app\arm_config.json` and
`sequences\` as before. [app/paths.py](app/paths.py) is the only place that decides
this, and **Arm → About** shows the paths in use.

### Antivirus, SmartScreen and locked-down machines

An unsigned executable is treated with suspicion by three separate mechanisms. They
have different fixes, so it is worth knowing which one you have hit.

**1. ASR prevalence rule - a managed corporate policy.** If the machine is enrolled in
Intune or similar, the rule *"Block executable files from running unless they meet a
prevalence, age, or trusted list criterion"* refuses to launch any newly built exe.
It fails with a bare `Access is denied`, and Event Viewer logs
**Event ID 1121** under `Microsoft-Windows-Windows Defender/Operational` with rule GUID
`01443614-CD74-433A-B99E-2ECDC07BFC25`. This has nothing to do with what the program
does - copying `where.exe` out of System32 under a new name gets blocked identically.
Check with:

```powershell
Get-WinEvent -FilterHashtable @{LogName='Microsoft-Windows-Windows Defender/Operational'; Id=1121} -MaxEvents 5
```

Nothing in the build clears this. It needs one of: a code-signing certificate the
organisation trusts, an ASR exclusion added by IT for the install path, or enough
downloads worldwide for the file to earn prevalence. If your recipients are colleagues
on the same policy, sort this out with IT before sending anything.

**2. Defender's heuristics on the file itself.** The shipped build is `--onedir` rather
than `--onefile` partly for this: a onefile exe unpacks itself into `%TEMP%` and
executes from there, which resembles a malware packer and draws more scrutiny. The
folder build also starts faster and the installer hides the folder, so there is no
reason to prefer onefile unless you specifically want a single portable file. If a
build is ever flagged as an actual named threat rather than an unknown one, report the
false positive at <https://www.microsoft.com/en-us/wdsi/filesubmission>; those are
usually cleared in a day or two.

**3. SmartScreen - reputation, not behaviour.** On an ordinary unmanaged machine this
is the only one you will meet. The recipient sees *"Windows protected your PC - unknown
publisher"* on first run; **More info → Run anyway** clears it, permanently for that
file. Only a signature removes the prompt itself:

| | Effect |
|---|---|
| Unsigned (now) | Warning on each fresh download until the file earns reputation. |
| Azure Trusted Signing | Around $10/month; names you as publisher, reputation accrues. |
| Traditional OV certificate | A few hundred a year, on a hardware token. Same effect. |
| EV certificate | Dearer, but carries SmartScreen reputation immediately. |

Once you have a certificate, sign both the app exe and the setup exe:

```bat
signtool sign /fd SHA256 /tr http://timestamp.digicert.com /td SHA256 ^
  build\app\RoboticArmStudio\RoboticArmStudio.exe
rem then re-run build.bat so the installer wraps the signed exe, and sign the result
signtool sign /fd SHA256 /tr http://timestamp.digicert.com /td SHA256 ^
  dist\RoboticArmStudio-1.0.0-Setup.exe
```

Whoever receives it still has to flash the Arduino and wire a separate servo supply.
The installer puts `WIRING.md` and the sketch in the Start menu for exactly that reason.

## Troubleshooting

| Symptom | Cause |
|---|---|
| No ports listed | Board not plugged in, or a CH340 clone missing its driver. Press Refresh. |
| Connect fails, "Access is denied" | The Arduino IDE Serial Monitor is holding the port. Close it. |
| Connects but nothing moves | Servo power supply missing or its ground not tied to the Arduino's. |
| Board resets mid-move | Servos drawing through the Uno's regulator — use a separate supply. |
| Arm jitters at rest | Normal for cheap analog servos under load. Press **Relax** when parked. |
| A joint runs the wrong way | Tick **Invert** for it in Arm → Joint setup. |
| Playback overshoots the mechanism | Lower Speed, and set real travel limits in Joint setup. |

> The app waits ~1.8 s after opening the port because the Uno reboots when DTR asserts.
> That pause is expected, not a hang.
